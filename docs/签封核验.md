# 本地签封与收件核验（离线）

适用场景：把扫描图像、人工校订文字与页序交付给外部单位长期保存，需要证明
**对方收到的内容就是本次确认的版本**，而不是仅给压缩包改了名字。

实现位于 `paperflow/sealing/`，仅依赖 Python 标准库与系统 `openssl`（≥3.0，
Ed25519），无第三方包，签发方与收件方都可完全离线运行。

## 威胁模型与对应机制

| 要求 | 机制 |
| --- | --- |
| 证明内容与确认版本一致 | 每个交付文件记录相对路径、字节数、SHA-256；每页单独记录图像哈希与人工校订文字哈希；页序 `page_order` 单独入清单 |
| 不能只靠改压缩包名字蒙混 | 哈希只覆盖文件**内容**与清单结构，不覆盖 ZIP 压缩级别、条目顺序、时间戳、文件名。重新压缩/改名核验仍通过且版本差异为零 |
| 替换图像可区分 | 命中 `payload/content_mismatch`，并在版本 diff 中标记具体页 `image_replaced` |
| 调页序可区分 | `order_changed` 与逐页 `before_seq → after_seq`；纯调页不计入图像/文字修改 |
| 改文字可区分 | 页级 `text_modified`（文字哈希变化、图像哈希不变），与 `image_replaced` 明确区分 |
| 收件方先确认签封者受信 | 本地受信公钥库 `trust/`；未受信时整体判不可信（退出码 1），但仍单独报告签名本身是否有效，区分“不信任的人签的”与“签名损坏” |
| 核验不污染现有档案 | 核验全程只读；报告默认只打印，`--report` 也只能写到交付件之外；OpenSSL 临时文件仅存在系统临时目录 |
| 旧版本不能被悄悄改写 | 交付件落盘即 `0440` 只读；`seal` 对已存在输出路径直接拒绝；本机另存只追加的哈希链登记表，任何一行被改/删/重排都会在 `log --verify-chain` 的对应位置断链 |
| 确认后、签封前来源被改动 | `seal` 会复扫来源并与确认草稿逐项比对，发现变化即中止，不产生交付件 |

## 交付件结构

```
xxx.sealed.zip
├── payload/                     # 原始交付文件，路径与来源一致
│   ├── processed/ originals/ thumbs/ sources/ ...
│   ├── metadata.json            # PaperFlow 归档元数据（含 order/sources/ocr）
│   └── delivery-notes/          # 签封时附加的交接说明
└── META-INF/
    ├── manifest.json            # 签封清单（含 seal 签名字段）
    ├── signature.bin            # Ed25519 原始签名
    ├── signer-public.pem        # 签发者公钥（信任判定仍以本地受信库为准）
    └── VERIFY.txt               # 离线核验说明（含纯 openssl 手工验签步骤）
```

签名对象是“把 `seal.manifest_sha256` 与 `seal.signature_hex` 还原为空字符串后
的规范化清单字节”（键排序、无空白的确定性 JSON）。核验端仅凭包内清单即可
确定性复算同一字节序列，无需额外文件。

## 操作流程

### 签发方（本工作台）

```bash
# 1. 生成签发密钥（私钥 0600，仅存本机；公钥通过独立可信渠道交给收件方）
python -m paperflow.seal keygen --name "甲档案馆交付岗"

# 2. 扫描来源，生成“交付内容确认单”。来源支持 PaperFlow 导出 ZIP 或普通目录；
#    可重复 --note 附加交接说明
python -m paperflow.seal prepare --source 交付.zip --draft-dir ./draft-v1 \
    --note 交接说明.txt

# 3. 人工核对 draft-listing.txt 后签封（签封前自动复扫，确认后有改动会拒绝）
python -m paperflow.seal seal --draft-dir ./draft-v1 \
    --output ./out/甲卷_2026-11-12.sealed.zip

# 4. 复核本机登记表哈希链
python -m paperflow.seal log --verify-chain
```

### 收件方（另一台工作台）

```bash
# 1. 通过独立渠道取得签发者公钥并加入受信库（勿只信任包内公钥）
python -m paperflow.seal trust add --public-key sender-public.pem --name "甲档案馆交付岗"
python -m paperflow.seal trust list

# 2. 核验：先判受信，再验签名，再逐文件/页序/文字比对
python -m paperflow.seal verify --bundle 甲卷_2026-11-12.sealed.zip \
    --report ./核验报告.json
# 退出码：0 通过；1 不可信或内容被改动；2 用法/环境错误

# 3. 与上一版比较，定位哪一页、哪项说明发生变化
python -m paperflow.seal verify --bundle 新版.sealed.zip --baseline 旧版.sealed.zip
# 或只做版本差异：
python -m paperflow.seal diff --before 旧版.sealed.zip --after 新版.sealed.zip
```

无 Python 时可用 OpenSSL 3.x 手工验签（详见包内 `META-INF/VERIFY.txt`）：

```bash
openssl pkeyutl -verify -pubin -inkey signer-public.pem -rawin \
  -in manifest.json -sigfile signature.bin
```

## 关键安全边界

- **信任锚点在本地**：包内公钥只用于展示与诊断，是否受信以收件方 `trust/` 库为准。
- **只读不是不可变存储的替代品**：`0440` 与拒绝覆盖防止常规误操作；面对本机
  管理员级对手，应把签封后的交付件复制到 WORM/对象存储锁定，并定期
  `log --verify-chain` 复核登记表。
- **私钥不出本机**：`keys/<指纹>/private.pem` 权限 0600；备份密钥库时需单独
  采取保护措施。
- **待验数据隔离**：待验交付件应放在独立目录，运行 Python 时建议加 `-I`，
  避免该目录下的同名模块（如伪造的 `json.py`）被解释器加载。
- **大小与数量上限**：单批 5000 个文件、解压总量 512MB；拒绝符号链接、
  加密成员、越界路径与清单之外的夹带成员。

测试：`python -I -m unittest discover -s tests -p 'test_sealing.py'`（16 项，
覆盖重压缩不误报、换图/调页/改文区分、不受信、伪造清单、只读核验、
登记表断链、确认后改动拒绝、夹带成员等）。
